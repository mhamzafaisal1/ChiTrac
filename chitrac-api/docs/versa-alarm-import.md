# Versa alarm import

This is a standalone, one-time import into `config-alarm-versa`. It does not run
at application startup or as part of `init:config`. It does not change the Versa
POST route, datafeed, simulator, or the existing `config-alarm` collection.

## Source and mapping

`data/versa-alarms.json` contains only the approved ID, STOP and English columns
from `feeder error text with id all translations.csv`, a semicolon-delimited file
with 107 records (IDs 0–106). Other language columns are not bundled or imported.
The English text is preserved as supplied. The source STOP values `yes` and `no`
were converted to JSON booleans; they must never be converted using string truthiness.

IDs **24, 68 and 85** are omitted because their STOP value is `yes/no`, pending
BIKO clarification. There are **104 approved records: 26 stopping and 78 non-stopping**.

The importer validates records against the existing alarm schema:

| Field | Value |
| --- | --- |
| `id` | Original numeric ID, including zero |
| `name` | Original `English [en]` text |
| `stop` | Boolean from STOP |
| `fault` | Equal to `stop`, per Rob's instruction for this import |
| `color` | `Red` when stopping, `Yellow` otherwise |
| `active` | `true` |
| `jam` | `0` |
| `timestamps.create`, `.active`, `.update` | Import time as BSON Dates |
| `_id` | Generated by MongoDB |

`fault = stop` is an import rule only. The shared schema continues to allow the
two flags to vary independently. IDs are unique within this catalog; the same
numeric ID may refer to a different alarm in Chicago's `config-alarm` collection.

## Deploy and run on Alpha

Deploy these changes with the API's normal dependencies installed. From the
`chitrac-api` directory, validate the bundled source first:

```powershell
npm run import:alarms:versa
```

The default (also available as `--dry-run`) is offline and makes no database
connection or writes. It does not check existing database records for conflicts.

Confirm Alpha's `MONGO_CONN_STRING` points to the intended database explicitly.
The command loads `.env` beside the API's package.json regardless of the working
directory; existing environment variables take precedence, as with `init:config`.
Then run on Alpha:

```powershell
npm run import:alarms:versa -- --apply
```

The command prints the selected database, inserts missing definitions, and reads
them back to verify all 104 approved IDs, mapped fields, and BSON timestamps.
It creates a unique `id` index on `config-alarm-versa`.

Existing identical records are left untouched, including their timestamps and
ObjectIds. Any conflicting approved ID aborts preflight before writes. Existing
unrelated IDs, including deferred IDs if already present, are not deleted or changed.
Duplicate IDs anywhere in the collection prevent unique-index creation.

The import is not a transaction. A database failure or concurrent import can leave
a partial result; the command exits nonzero and can be retried after resolving the
cause. Missing IDs are filled on retry, without replacing existing definitions.
Run one importer at a time. No reset, deletion, or overwrite command is provided.

## Integration boundaries

The [Versa POST route](versa-alarm-messages.md) resolves `status.alarmCode` against
this catalog and enriches the stored status with its configured `stop` and `name`.
Further machine-specific integration remains separate work. Existing
configuration websocket discovery already includes public `config-*` collections,
so it can expose this catalog after import. The explicit standard configuration
export list does not include this collection; use database backup tooling if a
backup of the imported catalog is needed. No export or frontend behavior is added
by this task, and the bundled source permits recreating the catalog after a reset.
